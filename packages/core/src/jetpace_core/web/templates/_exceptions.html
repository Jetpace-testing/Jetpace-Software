{# The exceptions panel - the design's "Recent Alarms", and deliberately not called that. THERE IS NO ALARM MODEL IN THIS SCHEMA. No limits table, no alarm row, no severity, no acknowledgement (architecture.md §10). The design's panel has Severity and a Status of Active or Acknowledged, both of which need the subsystem that does not exist. What does exist is three honest kinds of exception: silent a device has stopped answering, or never started. The shell knows this, because it is a fact about data arriving rather than about what the data means. suspect the poller itself flagged the sample: 1 substituted from a device's own log, 2 suspect. Also the shell's to know. excursion a reading outside a specification. Only a product can say this, because only a product has the specification - a cleanroom cascade holds the clean side above the dirty side - so these arrive through Product.events. The state chip is the design's, with the one distinction that is genuinely available without an acknowledgement model: still happening, or recovered. Nothing here is stored and nothing can be acknowledged, which the note at the bottom says out loud - a panel that looks like an alarm list would otherwise be read as one. #} {% import "_icons.html" as ico %} {% set BADGE = {'silent': ('offline', 'Silent'), 'suspect': ('warning', 'Suspect'), 'excursion': ('critical', 'Excursion')} %}
