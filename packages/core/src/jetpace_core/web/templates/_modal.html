{# The add-device modal: the real form. IT USED TO EXPLAIN WHY IT COULD NOT EXIST. The chrome was the design's and the content said devices were commissioned from a gateway sheet, because there was no write path - and the note said the application role "has no write grant on the device tables", which was simply wrong. setup_postgres.py has granted it INSERT on every table except `reading` since the database was first provisioned. The write path was unbuilt, not forbidden. WHAT THE OPERATOR SUPPLIES is where the instrument is and what it is called: the converter's address, the slave id, the device type, a name, and the low and high set points. WHAT THEY DO NOT supply is anything about registers - which addresses to read, what the values mean, how often to scan - because that comes from the register map in the product package, pinned to the datasheet by a test. There is no field on this form that can put a wrong address on a device. TWO STEPS, deliberately. `Check the device` reads it live over Modbus and shows what it is reporting; `Commission` writes the rows. Seeing 12 Pa come back before committing is the difference between commissioning an instrument and commissioning a guess - and the reading it was accepted on goes into the audit row, because it is the one measurement nobody can reconstruct afterwards. A device that does not answer can still be commissioned - installed and not yet powered is an ordinary case - but only with a reason, which is recorded. #} {% import "_icons.html" as ico %}
